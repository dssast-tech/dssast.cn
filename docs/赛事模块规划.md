## 1. 需求原文拆解

文档很短，但每句话都对应一块工作量：

| 原文 | 拆出来的东西 |
|------|------------|
| 整体参考 `mselab.tsinghua.edu.cn` | 视觉与信息架构照抄思路：选手端 + 赛事卡片列表 + 赛事详情 + 在线报名 + 提交中心 |
| 「赛事卡片包括院系的（赛事部组织报名）和校内校外的（不组织报名）」 | **两类赛事**：`internal` 可报名/可提交作品；`external` 只做介绍 + 推送/资源链接 |
| 「前者需要和后面的报名模块关联，可以报名/提交作品」 | 赛事 ↔ 报名记录 ↔ 作品，三者要能串起来 |
| 「后者需要做一个简单介绍，附上相关推送/资源链接」 | 就是 v1 的 links 聚合，这类赛事不做报名 |
| 「赛事卡片点开以后的组织，可以参考这个界面，非常简洁明了」 | 详情页 = **banner（状态 + 标题 + 关键日期 + 阶段条）+ 分区内容**，参考 fig2 |
| 「希望有一个类似的报名模块，选择比赛后收集相关信息」 | 站内报名表单：选赛事 → 填表 → 提交 → 后台看名单 |
| 「这个网站本身提供面向校外用户的报名，赛事部希望保留」 | **校外用户也要能报名** → 需要前台账号体系，不是只服务校内 |
| 「操作做的简单、模块化一些，比如像腾讯问卷创建新问卷那样」 | 表单要**可配置**：建模板 → 选字段 → 挂到赛事上，而不是每场比赛写死一个 HTML 表单 |
| 「其它页面也有它的作用，开发者可以参考」 | 参考站还有：我的主页、我的信息、提交中心、活动报备、我的作品、我的点赞、团队管理 → 至少「我的报名/我的作品/团队」要想清楚做不做 |

### 参考站实测到的字段（`/prod-api/competition/info/public/featured`）

公开接口返回 7 场赛事，字段能反推出它的模型，对我们很有参考价值：

```
name, publishDate, description, year, competitionType, status, shelfStatus,
organizer, undertakeOrganizer, participants, teamRequirements,
registerRosterMemberMin/Max, registerRosterMemberMax,
showEnrollment, showSubmission, showGallery, showHistory, showTopicRelease,
scheduleJson[]      ← 阶段/时间线，每项是「时间 + 标题 + 说明」的整段文本
competitionFlowJson ← 流程（这场为空）
submissionTargetJson, workRequirementsJson, awardSettings, forumFeesJson,
totalParticipants/Count, totalSchools/Count, totalWorksCount, contestHistory,
consultationHotline, consultationEmail, wecomGroupQrUrl
```

两个结论：

1. 它的时间线就是 `scheduleJson` 这种「数组 + 每项一段富文本」，**不是**我们想象的严格起止时间结构。我们可以做得更结构化（有 `start/end` 才能算「进行中」），但别过度设计。
2. 它的赛事配置项非常多（是否展示报名、是否展示提交、队伍人数上下限、赛道、奖项、论坛……）。**我们 6 个人 3 周做不完这个体量**，必须砍。

## 3. 五个必须先拍板的事（不定就没法开工）

### 3.1 账号与「校内身份」怎么认定 🔴 最高优先级

参考站用的是清华统一身份认证（`/auth/oauth`），报名页还能选「学生 / 业界」。我们大概率**拿不到学校 SSO 接入**（要走信息化办审批，学生会项目基本没戏）。那么只有三条路：

| 方案 | 做法 | 代价 |
|------|------|------|
| A. 自建账号 + 邮箱验证 | 注册时发验证码；`@mails.tsinghua.edu.cn` / `@mail.tsinghua.edu.cn` 自动标为「校内」，其他为「校外」 | 最现实；需要能发邮件（SMTP，见 3.3） |
| B. 自建账号 + 学号人工审核 | 注册后填学号，赛事部后台点「通过」 | 人力成本高，报名高峰期会堵 |
| C. 完全不要账号，报名表单填邮箱/手机 | 最轻；但「我的报名/我的作品/团队」全做不了，改报名也做不了 | 只能做一次性收集，和「腾讯问卷」没区别 |

**我建议 A**，并且明确：校外用户一视同仁注册，只是身份标记不同、审核策略可不同。

### 3.2 表单能力的边界（决定是 2 天还是 2 周）

「像腾讯问卷那样」可以是三个量级：

- **L1 固定字段**：姓名/学号/院系/手机/邮箱/组队/作品名。改字段要改代码。—— 2 天
- **L2 模板 + 字段库**：后台能建模板，从固定字段库里勾选、排序、设必填。字段类型 6 种。—— 1 周
- **L3 自由建题**：任意加题、任意类型、逻辑跳转、分页、配额。—— 3 周起，不建议

**建议 L2**：字段类型限定 `单行文本 / 多行文本 / 单选 / 多选 / 数字 / 文件`，每题可设必填、说明、占一列还是整行。够用，且后台 30 秒能建完一场比赛的报名表。

### 3.3 邮件与文件（两个必踩的坑）

- **邮件**：WordPress 默认 `mail()` 基本发不出去（会被当垃圾邮件或直接失败）。注册验证码、报名成功通知都依赖它 → 必须配 SMTP（学校邮箱或 QQ/企业邮箱授权码），并且做「发送失败降级为站内提示」。
- **文件**：作品提交要限类型（pdf/zip/png/jpg/mp4）、限大小（建议单文件 ≤ 50MB、单次 ≤ 3 个）、限时间（截止后禁止）。服务器是轻量应用服务器，磁盘和带宽都紧 → 大文件建议直接传对象存储（OSS/COS），别塞 `wp-content/uploads`。

### 3.4 审核与导出

报名要不要审核？建议：默认「提交即有效」，后台可标记「无效/重复」，并提供 **CSV 导出**（赛事部要拿名单做通知、分组、发奖）。导出是刚需，别漏。

### 3.5 和「静态化」的矛盾

10/19 说公开页静态化，但报名、作品提交、我的报名都是**动态且要登录**的。结论只能是：**公开信息页可静态，交互页必须动态**。这条要写进方案，否则后面会反复。

## 4. 数据模型 v2

### 4.1 实体关系

```
competition (赛事)
  ├── stages[]        阶段（时间线）
  ├── links[]         推送/资源/结果
  ├── form_template   报名表单模板（可复用）
  └── submission_cfg  作品提交配置
        │
        ├── registration (报名记录) ── user
        │        └── submission (作品) ── files[]
        └── ...
user (校内/校外)
```

### 4.2 赛事（扩展 `dssast_competition`）

保留现有 5 个字段，新增：

| 字段 | 类型 | 说明 |
|------|------|------|
| `dssast_type` | enum | `internal` 院内（赛事部组织）/ `external` 校内校外（仅介绍） |
| `dssast_signup_mode` | enum | `none` / `form`（站内表单）/ `link`（外链） |
| `dssast_form_template_id` | int | 关联表单模板 |
| `dssast_allow_submission` | bool | 是否收作品 |
| `dssast_submission_deadline` | datetime | 作品截止（可晚于报名截止） |
| `dssast_team_min` / `dssast_team_max` | int | 组队人数，0/1 表示个人赛 |
| `dssast_audience` | string | 参赛对象（文案） |
| `dssast_venue` / `dssast_organizer` | string | 地点 / 主办 |
| `dssast_result_url` | url | 结果/榜单 |
| `dssast_stages` | JSON | 见 v1 §6.2，不变 |
| `dssast_links` | JSON | 见 v1 §6.3，不变 |

状态仍按 `registration_start / registration_end / date` 自动推导（v1 §6.4），`external` 类型不显示报名 CTA。

### 4.3 表单模板（新表 `wp_dssast_form`）

```
id, name, schema(JSON), created_by, created_at, updated_at
```

`schema` 示例：

```json
{
  "fields": [
    { "key": "name",   "label": "姓名",   "type": "text",     "required": true,  "width": "half" },
    { "key": "sid",    "label": "学号",   "type": "text",     "required": true,  "width": "half" },
    { "key": "dept",   "label": "院系",   "type": "select",   "required": true,  "options": ["笃实书院", "其他"] },
    { "key": "track",  "label": "赛道",   "type": "radio",    "required": true,  "options": ["算法", "硬件"] },
    { "key": "team",   "label": "队伍成员","type": "textarea", "required": false, "width": "full" }
  ]
}
```

### 4.4 报名记录（新表 `wp_dssast_registration`）

```
id, competition_id, user_id, form_id, answers(JSON),
team_name, status(pending/valid/invalid), ip, created_at, updated_at
UNIQUE(competition_id, user_id)   ← 同一比赛一人一条，允许改
```

**为什么用自定义表而不是 post/meta**：报名量可能上千，后台要按赛事筛选、分页、导出 CSV、统计赛道分布；用 `wp_postmeta` 存 JSON 查询会非常难受，导出要 N+1 查询。

### 4.5 作品（新表 `wp_dssast_submission`）

```
id, competition_id, registration_id, title, note,
files(JSON: [{name,url,size,mime}]), version, submitted_at
```

允许截止前覆盖（`version` 自增），截止后锁定；是否允许迟交由赛事配置。

### 4.6 用户

用 WordPress 用户 + 自定义 role `dssast_participant`，额外 user_meta：

```
dssast_identity: internal | external     （由邮箱域名或人工审核决定）
dssast_school, dssast_major, dssast_grade, dssast_phone
```

## 5. 页面与路由

| 页面 | 路由 | 登录 | 说明 |
|------|------|------|------|
| 赛事列表 | `/events/` | 否 | 两类卡片；筛选：全部 / 院内 / 校内校外；搜索；排序 |
| 赛事详情 | `/events/{slug}/` | 否 | banner + 阶段条 + 分区内容 + 报名/提交 CTA |
| 报名表单 | `/events/{slug}/register/` | 是 | 渲染表单模板；已报名则显示「已提交，可修改」 |
| 作品提交 | `/events/{slug}/submit/` | 是 | 仅 `allow_submission`；截止后只读 |
| 登录 / 注册 | `/login/`、`/register/` | — | 校外用户可注册 |
| 我的报名 | `/me/registrations/` | 是 | 列表 + 状态 + 改报名 |
| 我的作品 | `/me/works/` | 是 | 列表 + 重新上传 |
| 后台 | `/wp-admin/` | 管理员 | 赛事 / 表单模板 / 报名名单 / 导出 |

> URL 仍要收敛：现在导航指 `/events/`（空白页），CPT 归档在 `/competitions/`。建议对外统一 `/events/`，`/competitions/` 301。

## 6. 接口

| 方法 | 路径 | 权限 | 用途 |
|------|------|------|------|
| GET | `/wp-json/dssast/v1/competitions` | 公开 | 列表（含 type/stages/links 摘要） |
| GET | `/wp-json/dssast/v1/competitions/{slug}` | 公开 | 详情 + 表单结构（只返回字段定义，不含他人答案） |
| POST | `/wp-json/dssast/v1/competitions/{slug}/registrations` | 登录 | 提交/修改报名 |
| GET | `/wp-json/dssast/v1/me/registrations` | 登录 | 我的报名 |
| POST | `/wp-json/dssast/v1/competitions/{slug}/submissions` | 登录 | 提交作品（multipart） |
| GET | `/wp-json/dssast/v1/admin/registrations?competition=` | 管理员 | 后台名单 |
| GET | `/wp-json/dssast/v1/admin/registrations.csv?competition=` | 管理员 | 导出 |

安全：所有写接口 `wp_rest` nonce + 登录校验；答案按 schema 白名单过滤（未知 key 直接丢弃）；文件走 `wp_handle_upload` 并校验 MIME 白名单；同一用户同一赛事重复提交做幂等（返回已存在记录）。

## 7. 后台操作流（「像腾讯问卷」具体长什么样）

```
赛事管理
 ├─ 赛事列表（状态 / 类型 / 报名数 / 作品数 / 快捷改状态）
 ├─ 新建赛事
 │    ① 基本信息（标题、封面、分类、简介、正文）
 │    ② 类型与报名（院内/校内外；报名方式：不报名/外链/站内表单）
 │    ③ 阶段（可增删排序，v1 的 stages）
 │    ④ 链接（推送/资料/结果）
 │    ⑤ 作品提交（是否开启、截止时间、文件限制）
 └─ 报名名单（按赛事筛选 → 表格 → 标记无效 → 导出 CSV）
表单模板
 ├─ 模板列表（使用次数）
 └─ 新建模板：左侧字段库（6 种）→ 拖/点进右侧表单 → 设必填/说明/半栏 → 预览 → 保存
```

关键体验点：**新建一场比赛 = 选一个现成模板，30 秒能发出去**；不要让赛事部同学每次重新建题。

## 8. WP 落地方式（技术选型，给review用）

- 赛事：继续用 CPT（沿用现有代码和短代码，风险最小）。
- 表单模板 / 报名 / 作品：**自定义表**（`dbDelta` 建表，带 `db_version` 选项做迁移），不用 CPT + meta。
- 前台账号：WP 用户 + 自定义 role + 前台登录页（`wp_signon`），不用 WooCommerce/会员插件（太重）。
- 表单渲染与校验：一个 `Dssast_Form` 类，`render(schema)` + `validate(schema, input)`，前后端同源规则。
- 文件：先直传 `uploads`（限 50MB），量起来再换对象存储；上传目录禁止 PHP 执行。
- 邮件：配 SMTP（`phpmailer_init` 钩子），失败只记日志，不阻塞报名。
- 导出：`fputcsv` 流式输出，中文 Excel 兼容加 BOM。

## 9. 分期（我认为最合理的切法）

一个人做全部，**4–6 周**。强行一次做完必然延期，建议分三期，每期都能独立上线：

| 期 | 内容 | 工期 | 上线形态 |
|----|------|------|---------|
| **MVP1 信息模块** | 两类赛事 + 列表页 + 详情页 + 阶段时间线 + 链接聚合 + 状态自动推导；报名暂时走外链 | 1.5 周 | 完全可用，先替换 `/events/` 空白页 |
| **MVP2 报名模块（固定字段）** | 前台注册登录 + 站内报名 + 我的报名 + 后台名单 + CSV 导出 | 2 周 | 院内赛事可线上报名 |
| **MVP3 配置化 + 作品** | 表单模板编辑器（L2）+ 作品提交 + 文件限制 + 邮件通知 | 1.5–2 周 | 赛事部自助建表 |

先做 MVP1 的好处：10/19 提的「赛事页（分类 tag、搜索、排序）」当场就有交付物，报名模块的账号/邮件/文件风险也留出了决策时间。

## 10. 风险

1. **SSO 拿不到** → 只能自建账号，校外用户与校内用户混在一个用户表，身份靠邮箱域名判定，可被伪造（清华邮箱域名不可伪造，但「校外用户填清华邮箱」也可能）。低风险，可接受。
2. **邮件发不出去** → 注册验证码卡死整个报名流程。必须第一周就把 SMTP 打通并做降级（验证码页面提示「收不到可联系赛事部」+ 后台手动改密码）。
3. **文件把服务器塞满** → 轻量服务器磁盘通常 40–60G，视频作品很快就满。必须限大小 + 定期清理 + 备份策略。
4. **并发**：报名截止前 10 分钟集中提交，自定义表 + 事务要小心；用唯一索引挡重复，不要靠「先查再插」。
5. **静态化冲突**：见 §3.5，公开页静态、交互页动态，架构上要分开，别指望一套静态生成覆盖全部。
6. **直推 main 即上线**：没有灰度和回滚，报名期间一定用分支 + PR。
7. **范围蔓延**：「我的点赞」「团队管理」「活动报备」这些参考站功能，除非明确要做，否则不进 MVP。

## 11. 要拍板的问题（按阻塞程度排序）

1. 🔴 校内身份怎么认定？能接学校统一身份认证吗？（大概率不能 → 邮箱域名方案要不要？）
2. 🔴 校外用户要不要开放注册？开放后是否需要赛事部审核才可报名？
3. 🔴 表单配置做到 L1 / L2 / L3 哪一级？（我建议 L2）
4. 🟠 作品提交这次做不做？做的话文件上限多少、要不要对象存储？
5. 🟠 报名需要审核吗？还是提交即有效、后台只做「标记无效」？
6. 🟠 「我的主页/我的作品/团队管理」这次范围含不含？（建议不含）
7. 🟡 邮件通知发不发？（发 → 谁提供 SMTP 账号）

## 附录 A：表单三级能力对照（给组长看的一页）

场景：赛事部想在报名表里加一个「是否申请住宿」的单选项，并让它在后台名单和导出里出现。

|---|---|---|---|
| 谁改 | 找你改代码 | 赛事部自己在后台点 | 赛事部自己建 |
| 改一次花多久 | 改代码 + 提 PR + 部署，0.5–1 天 | 30 秒 | 3 分钟 |
| 要发版吗 | 要 | 不要 | 不要 |
| 字段类型 | 写死的 6 个 | 6 种：单行/多行/单选/多选/数字/文件 | 无限，还能加评分、矩阵、排序 |
| 逻辑跳转（选团队赛才显示队友） | 写死 | 不支持 | 支持 |

| 开发量 | 2 天 | 5–7 天 | 3 周+ |
| 适用 | 一年就两三场比赛、字段基本不变 | **推荐**：不同比赛字段不同，但题型简单 | 要做成通用问卷平台 |

L2 的一周时间实际花在：

1. 渲染器 + 6 种字段类型 + 前端校验 —— 2 天
2. 后台「建模板」界面（字段库勾选、上移下移、必填、半栏、预览）—— 2 天
3. **最容易被低估的**：报名记录按模板动态存、后台名单动态列、CSV 表头跟着字段走 —— 2 天

L2 的两个坑，提前定：

- **模板改了，已完成报名的记录怎么办？** 建议每条报名记录存一份 schema 快照（或模板 ersion），老记录按老字段渲染，不追着改。
- **删字段 ≠ 删数据。** 字段从模板移除后，历史答案保留在 JSON 里，只是不再显示；别做级联删除。

## 附录 B：作品文件的存储选型

### B.1 先算体量

| 场景 | 单份大小 | 一场 200 队 | 一年 4 场 |
|---|---|---|---|
| 只收 PDF / 代码压缩包 | 5–20 MB | 1–4 GB | 4–16 GB |
| 收演示视频（3 分钟 MP4） | 100–200 MB | 20–40 GB | 80–160 GB |

结论：**不收视频，服务器本地盘就够；收视频，必须对象存储。**

### B.2 四种方案

| 方案 | 成本（约） | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| A. 服务器本地盘 | 含在 500 元/年服务器内；加数据盘约 0.5 元/GB/月 | 零配置、内网读写快、不用备案域名 | 扩容要停机；备份靠自己；轻量带宽 3–6 Mbps，评委下一个 100MB 文件要 2–4 分钟 | 只收 PDF 时可用 |
| B. 对象存储（腾讯云 COS / 阿里云 OSS） | 标准存储 0.09–0.12 元/GB/月；100GB 存储包约 99 元/年；外网下载 0.25–0.5 元/GB，上传和内网流出免费 | 前端直传不占服务器带宽；容量无上限；生命周期转归档 0.03 元/GB/月；自带多副本 | 要开子账号、配密钥、配 CORS；下载流量单独计费 | **推荐**，正式运营就用它 |
| C. 第三方网盘 / 表单附件 | 免费或几十元 | 零开发 | 无法鉴权、链接会失效、评审导出痛苦、隐私不可控 | 只适合临时过渡 |
| D. 院系 NAS / 学校云盘 | 免费 | 免费 | 无公网 API、离校失效、无法和网站集成 | 不推荐 |

### B.3 推荐组合与预算

`
网站：轻量应用服务器（现有，约 500 元/年）
文件：COS/OSS 私有 Bucket，前端预签名直传
下载：后端签发 10 分钟有效的预签名 URL，评委登录后才能拿
归档：比赛结束 90 天后转低频/归档存储，只保留获奖作品
`

按「一年 100GB 存储 + 每月 20GB 下载」估算：存储包约 99 元/年 + 流量约 120 元/年 ≈ **220 元/年**，在 500 元预算里能放下。

### B.4 必须一起定的五个参数

1. 单文件上限（建议 50MB；收视频再放到 200MB）
2. 单次文件数（建议 ≤ 3）
3. 类型白名单（pdf / zip / png / jpg；视频另开）
4. 是否允许截止前覆盖（建议允许，保留版本）
5. 内容责任：用户上传内容出事算站点的，必须有类型限制 + 赛事部人工过一遍 + 可下架

> 如果最终不做作品提交，以上全部不用管 —— 这也是建议 MVP1/MVP2 先不上作品的原因。

### C.1 表单：L2，但去掉拖拽

### C.3 一个必须先定的依赖

作品提交要回答「**这是谁提交的**」。两条路：

- **A. 免注册**：报名只填邮箱+手机，提交后发一个查询码；作品提交用「查询码 + 邮箱」进入。最轻，一周能把报名+作品跑通，和腾讯问卷体验一致。代价：没有「我的主页」，改报名靠查询码。
- **B. 注册制**：邮箱验证码注册，登录后报名、提交、看「我的报名」。体验完整，但要多做注册/登录/找回密码/邮件通道，至少 +1 周。

**我倾向 A 起步、B 后补**：A 的 
egistration 表已经存了 email/phone/token，将来加账号时按邮箱把历史报名绑定到用户即可，不用重做。

### C.5 建表草案

`sql
CREATE TABLE wp_dssast_form (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  schema LONGTEXT NOT NULL,        -- JSON: {fields:[...]}
  version INT UNSIGNED NOT NULL DEFAULT 1,
  created_by BIGINT UNSIGNED NOT NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  PRIMARY KEY (id)
);

CREATE TABLE wp_dssast_registration (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  competition_id BIGINT UNSIGNED NOT NULL,
  form_id BIGINT UNSIGNED NOT NULL,
  form_version INT UNSIGNED NOT NULL,
  schema_snapshot LONGTEXT NOT NULL,   -- 报名当时的字段定义
  answers LONGTEXT NOT NULL,           -- JSON
  email VARCHAR(190) NOT NULL,
  phone VARCHAR(32) NOT NULL,
  token CHAR(32) NOT NULL,             -- 免注册方案的查询码
  user_id BIGINT UNSIGNED NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'valid',
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY comp_email (competition_id, email),
  KEY comp_status (competition_id, status)
);

CREATE TABLE wp_dssast_submission (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  competition_id BIGINT UNSIGNED NOT NULL,
  registration_id BIGINT UNSIGNED NOT NULL,
  title VARCHAR(200) NOT NULL,
  note TEXT NULL,
  file_path VARCHAR(255) NOT NULL,
  file_name VARCHAR(255) NOT NULL,
  file_size BIGINT UNSIGNED NOT NULL,
  file_sha256 CHAR(64) NOT NULL,
  version INT UNSIGNED NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL,
  PRIMARY KEY (id),
  KEY reg (registration_id, version)
);
`

UNIQUE KEY comp_email 意味着同一邮箱在同一比赛只能报一次（含队伍）。若要允许一个邮箱报多个赛道，改成 (competition_id, email, track) 或去掉唯一键、只在业务层挡重复。
